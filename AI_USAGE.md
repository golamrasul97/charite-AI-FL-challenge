# AI Tool Usage Disclosure

I used AI tools throughout this challenge. This file lists which tools, what they produced, how I
checked their output, and which decisions were mine. The session-by-session record is in
[`docs/ai_log.md`](docs/ai_log.md).

## Tools

| Tool | Version / access date | Role |
|---|---|---|
| Claude Code (Anthropic), command-line assistant | Claude Opus 5, 23–27 Sep 2026; Claude Opus 5.5, 28 Sep 2026 | Main coding and writing assistant for every phase: read the data, wrote code, tests and documents, ran commands, and kept `docs/ai_log.md` |
| ChatGPT (OpenAI) | GPT-6 Astra, 25 Sep 2026 | A second opinion on the feature set in Task 3 (one analysis; see Task 3 below) |

No AI tool is used at run time: the submission is rules, NumPy and scikit-learn only, with no
pretrained models and no network access.

## How I worked with the assistant

- **A written brief with fixed rules.** Before starting I set up a working brief for the assistant
  (kept out of Git). It listed the challenge's rules as hard limits: never modify the protected
  challenge files, `run_submission.py` reads only `--train` and `--input`, no ground-truth access in
  the submission, no network or pretrained models, fixed seeds, validation used only for measuring,
  and "when unsure, ask".
- **I made every commit.** The assistant proposed commit messages; it never committed, pushed or
  rewrote history.
- **Discussion before code.** For each task I asked for the design or the options first, questioned
  them, and only then asked for code. For the privacy task I asked for step-by-step plain-language
  explanations until I could explain the mechanism myself.
- **A log for every phase.** The assistant wrote one entry per phase in `docs/ai_log.md`: what it
  generated, how it was verified, and what I changed or rejected. This file is built from that log.

Most of the code, tests and document text was generated by the assistant. My part was to set the
direction, make the decisions listed below, reject or change what did not convince me, and check
the results.

## Use by task

### Setup and error analysis (Phase 0–1)

- **Generated:** the baseline measurement (31.84 / 40, matching the challenge's stated value) and
  `scripts/error_analysis.py` with 9 tests. The tool lists every missed and extra identifier,
  diagnosis, medication and value, with context.
- **Verified:** the tool uses the official evaluator's own scoring functions, and a test checks that
  its totals equal `make evaluate`. The integrity check of the protected files passed.
- **My decisions:** I reviewed the script's design before it was written. I accepted a macOS
  substitute for the manifest check command (`shasum` instead of `sha256sum -c`).

### Task 1: de-identification (Phase 2)

- **Generated:** `src/deid/` (six layers: shapes, date type from context, names after cue words,
  repeats and names from e-mail addresses, addresses, conflict resolution) and 18 tests, including
  three hand-written notes in formats that do not occur in the data.
- **Verified:** de-identification score 1.0000 on train and validation with zero false positives;
  the three unseen-format notes gave no span beyond the hand-labelled set. The Phase 1 tool exposed a
  bug in the generated code: names ran across line breaks, which made every clinician span one word
  too long (85 false positives and 85 misses) while character recall still looked perfect. It was
  fixed and is now a test.
- **My decisions:** I accepted the three hand-written notes as the stand-in for the hidden formats,
  and required that the report present 1.0000 as coverage of known templates, not as an expected
  hidden-set score.

### Task 2: structured extraction (Phase 3)

- **Generated:** `src/extraction/` (lexicon, negation within the clause, unit conversion, value
  checks, smoking and allergy) and 116 tests.
- **Verified:** extraction 1.0000 on train and validation. Three new hand-written notes found five
  bugs that the labelled data never showed (for example, "AF ruled out" at the end of a list also
  removed the diagnoses before it). All five are now tests. I ran `scripts/error_analysis.py`
  myself to check the per-field results.
- **My decisions:** I accepted a whole-note scan instead of the section-first design in my brief
  (because six templates already use six different section headers), counting "suspected" and "?"
  as not active, the dataset's own mappings (bare "diabetes mellitus" → `type_2_diabetes`,
  phenprocoumon → `warfarin`), and not reading German "RR" as blood pressure.

### Task 3: federated learning (Phase 4)

- **Generated:** the first version (a NumPy logistic regression over seven files with 30 features),
  then the final `src/readmission.py` (scikit-learn `Pipeline(DictVectorizer, LogisticRegression)`,
  FedAvg written by hand, 9 features with fixed scaling), `scripts/run_experiments.py`, the files in
  `results/`, and 13 tests.
- **Verified:** repeated cross-validation on train (5 folds × 5 seeds); tests that the weighted
  average matches a hand calculation, that each local update sees exactly one hospital's rows and
  returns only weights and a count, and that results repeat exactly. The experiment script stops if
  its own selection rules pick settings different from those in the code.
- **What I rejected or changed:**
  - I rejected the first version after the validation readmission score fell from 0.7726 to 0.6786,
    and asked why it used 30 features when the starter used 5.
  - I asked for code as simple as the starter's; the seven NumPy files were replaced by one
    scikit-learn file with the same performance.
  - I asked for the challenge's own wording ("local / federated / centralized model", "site",
    "local updates") instead of the assistant's terms.
  - I asked for further experiments and dropped those that did not help: all structured and
    extracted fields together, random forest, gradient boosting (after I found a federated
    XGBoost paper; it turned out to be vertical federated learning with only a heuristic privacy
    guarantee), TabNet, and local fine-tuning per hospital.
  - I brought a ChatGPT analysis that suggested a 15–20 feature set, a check of the strong
    prior-admissions feature and leave-one-hospital-out testing. I had each suggestion tested
    instead of adopting it: prior admissions is not a shortcut (AUC 0.843 → 0.834 without it), no
    left-out feature helped, and leave-one-site-out became a result in the report.
  - **I chose the final 9-feature set** after comparing the candidates on cross-validation,
    5 000 simulated 50-case test sets and validation.

### Task 4: privacy (Phase 5)

- **Generated:** `src/privacy.py` (per-patient clipping and Gaussian noise inside each client,
  private FedAvg, a Rényi-DP accountant written by hand, the leakage demo, `privacy_summary.json`),
  27 tests, and the privacy sweep in `results/`.
- **Verified:** the accountant reproduces known reference values (T = 40: ε = 50.3 / 20.2 / 8.8 /
  4.1) and is never below the closed-form bound; with no noise, the private update equals a plain
  gradient step; the leakage demo recovers one patient's features exactly without noise.
- **My decisions:** I asked for no code until I understood the options. I questioned the
  recommendation against homomorphic encryption and had it compared fairly with differential
  privacy before choosing differential privacy. The assistant then proposed ten decisions (noise
  every round inside each hospital, the submission keeps the non-private model, an own accountant
  instead of a library, a rule for the reference ε fixed before running, and others); I accepted
  all ten after going through them.

### Packaging and documents (Phase 6)

- **Generated:** the full `experiment_summary.json`, safe handling of failing cases in
  `run_submission.py`, end-to-end tests (every output line checked against the official schema; a
  test fails if the submission opens any ground-truth file), the pinned `requirements.txt`, the
  Docker set-up, the README, `REPORT.md`, both figures and this file.
- **Verified:** 193 tests pass, locally and inside the Docker image; the offline Docker run
  (`--network none`) gives the same de-identification and extraction output as my Mac and
  probabilities within 2 × 10⁻¹⁵; the pinned requirements install on Python 3.11, 3.12 and 3.13. I
  had the report checked section by section against the template and the challenge README, and
  every number against `results/`. This found one wrong value (the starter's AUC spread) and one
  unclear sentence, both fixed.
- **My decisions:** summaries are recomputed from `--train` at every run instead of copied from
  files; every dependency is pinned so that nothing depends on the reviewer's environment; the
  Docker base stays `python:3.11-slim`; the starter's code is kept in the repository but unused.
  For the figures, I judged the README poster unsuitable as the report's architecture diagram and
  had a separate one made, stating in the text that the hospitals are simulated in one process. I
  found the privacy panel of that diagram too noisy and had it simplified. On review of the README
  figure I chose four fixes (no privacy step shown as part of the submitted pipeline, the
  readmission card labelled as cross-validation, outputs coming from the prediction step rather
  than the server, and a label for what is exchanged) and declined a fifth.

## What I designed or decided myself

- The working rules for the assistant and the phase order.
- Simplicity over complexity: one readable file for Task 3 in the starter's style, and only the
  challenge's own terms in code and results.
- Rejecting the first federated-learning version and choosing the final 9-feature set.
- Which alternatives to try (model families, feature sets, fine-tuning, the outside analysis), and
  dropping those that did not help.
- The privacy mechanism, after comparing differential privacy with homomorphic encryption.
- Keeping the submitted predictions on the non-private federated model and presenting the private
  model as a fully measured extension.
- Honest reporting: 1.0000 presented as template coverage, validation used only for measuring, and
  figures that do not claim more than the code does.

## How I checked AI output in general

- The official evaluator (`make evaluate`) after every change, and `scripts/error_analysis.py` for
  every per-field miss.
- 193 automated tests, including hand-written notes in formats the data does not contain.
- The integrity check of the protected challenge files (`MANIFEST.sha256`).
- Every number in `REPORT.md` and the README traced to a file in `results/` or to the evaluator.
- Asking for plain-language explanations of each design until I could explain it myself; when an
  explanation did not convince me, the design was changed or tested with numbers.
